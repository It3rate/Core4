# Core4 Locked Invariant Plan

This note captures the next demo and concept pass after primitive bases.

It is intentionally small. The exact invariant vocabulary may still change.

## 1. Goal

Show that a fusion does not only create a new result.

It also creates new properties that can be:

- frozen
- perturbed
- explored through compatible motion

The first page should visualize this directly.

## 2. Canonical Stance

The source of truth should remain Core4-native.

- no page-specific equation tags as the canonical meaning
- no graph-only fake curves as the canonical meaning
- no special-case inverse algebra layer

The page should be driven by real Core4 values and frozen structure, even if
the first pass still uses a thin demo-state wrapper.

## 3. Core Reading

An operation should be readable in two linked ways:

- forward construction: ingredients fuse into a new structure
- locked exploration: some revealed invariant of that structure is held fixed
  while one contributor is perturbed and the compatible response is observed

This means "inverse behavior" is not secondary. It is part of the physically
meaningful behavior of the fusion.

## 4. First Page

Working title:

- `Locked Invariants`

Placement:

- immediately after `Primitive Bases`

Presentation:

- reuse the same six primitive fused forms
- add one locked invariant mode at a time
- let one input be dragged
- compute the compatible second motion needed to preserve the frozen invariant
- trace the resulting locus of the dependent endpoint or corner

## 5. First Invariants

The first pass should not try to expose every possible invariant.

Start with one canonical revealed invariant for each family:

- self-interaction: lock the product-like magnitude
- directed segment: lock total span
- area / anti-area: lock bounded area
- complex / anti-complex: lock ray length

Later we can add alternate modes such as:

- lock sum instead of product
- lock width plus height instead of area
- lock orientation instead of length

## 6. Core Implication

This demo points toward a later core mechanism:

- frozen invariant
- perturbed participant
- compatible response
- traced path or motion family

Long-term this should likely become part of operation and relaxation rather
than remain only a page behavior.

## 7. First Implementation Pass

Keep the first implementation modest:

- one page
- six primitive forms
- one draggable input
- one dependent response
- one path trace per form

Do not solve everything generically yet.

The first goal is to make the locked-invariant behavior visible and
structurally honest.

## 8. Open Questions

- which revealed properties should count as canonical for each fusion
- whether anti-complex should be read as opposite turning or opposite signed
  orientation under the same locked magnitude
- how quickly this should move from demo-state logic into a reusable core
  invariant operation layer
- how this later connects to relaxation, loop behavior, and the general trolley
